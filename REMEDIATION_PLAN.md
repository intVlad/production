## 2. 🔥 Критичні розриви — ✅ ВСІ ЗАКРИТІ

### 2.1 Розподіл партії ✅
`BatchService.distributeBatch` тепер реально прив'язує вироблені деталі до піддонів: за `batch.getOperation().getAssembly()` + `pallet.getOwnerProduct()` знаходить відповідний `AssemblyInstance` (`AssemblyInstanceRepository.findByAssemblyIdAndProductInstanceId`), додає його в `pallet.getAssemblyInstances()`, переводить `PLANNED → IN_PROGRESS`, піддон `EMPTY → ASSEMBLING`. Покрито тестом `distributeBatch_LinksProducedAssemblyInstanceToPallet`.

### 2.2 Доступні операції при скані піддона ✅
`PalletService.getPalletByQr` більше не повертає захардкоджений порожній список — для кожного `AssemblyInstance` на піддоні шукає його задачі (`TaskRepository.findByAssemblyInstanceId`), фільтрує за статусом (READY/CREATED/ASSIGNED-своєму-воркеру) і, якщо піддон має відомий пост, за збігом поста. Повертає `TaskDTO`, а не сирі entity.

### 2.3 Контракт фронтенд/бекенд сканування піддона ✅
- `worker.js`/`manager.js`: прибрано неіснуючий виклик `GET /tasks/available?palletId=` — тепер використовується `availableOperations`, який вже приходить у відповіді `GET /pallets/qr/{code}`.

- Виправлено в обох файлах (`worker.js` і `manager.js` мали дубльовану копію того самого коду).

### 2.4 Резервування матеріалів ✅
- `TaskExecutionService.createIndividualTask` тепер резервує матеріали (`Operation.requiredMaterials` × `materialQuantityPerUnit`) одразу після створення задачі; при нестачі — задача йде в `BLOCKED` + `missingMaterials=true` замість тихого провалу.
- `completeTask` викликає `consumeMaterials`. Новий `cancelTask` викликає `releaseMaterialReservation`.
- `BatchService.createBatch`/`completeBatch` — та сама логіка, помножена на `plannedQty`/`actualQty`.
- `MaterialService.reserveMaterials` переведено на `Propagation.REQUIRES_NEW`, щоб невдала спроба резервування не позначала rollback-only всю зовнішню транзакцію створення задачі.
- `unblockTask` тепер повторно намагається зарезервувати матеріали (для випадку "постачальник поповнив склад") замість сліпого переведення в READY.

### 2.5 Розрахунок потреби матеріалів по серії ✅
`MaterialService.calculateSeriesRequirements` реально обходить Series → ProductModel → Assemblies → Operations → requiredMaterials, множить на plannedQuantity, рахує `required/available/reserved/deficit/status` (формула звірена з прикладом таблиці §15 ТЗ). Тип повернення змінено з `Map<Material,...>` (непридатний для JSON — Material як ключ мапи серіалізується в сміття) на `List<Map<String,Object>>`, узгоджено з `MaterialController.getRequirements`.

### 8.2 Брутфорс PIN-логіну — ✅ виправлено (найважливіша знахідка)
PIN — 4 цифри (10 000 комбінацій). `POST /api/auth/login/pin` без `workerId` перевіряє введений PIN проти **кожного** воркера в базі (включно з MANAGER/ADMIN); `GET /api/auth/workers` — публічний, без авторизації. Жодного rate-limit, лічильника невдалих спроб чи затримки ніде не було. На реально задеплоєному інстансі (напр. Render) це давало практичний шлях повної компрометації за лічені хвилини скриптом.
- [x] Новий `LoginRateLimiterService` — in-memory лічильник невдалих спроб, keyed по IP (`X-Forwarded-For` з фолбеком на `getRemoteAddr()`) і окремо по цільовому `workerId`, коли він відомий. 5 невдалих спроб за 5 хв → блокування на 15 хв (HTTP 429), успішний логін скидає лічильник. Підключено в обидва `login/pin` і `login/qr`.
- [x] Перевірено живим curl: 5× невірний PIN → 401, 6-та спроба (навіть із **правильним** PIN) → 429 з тим самим IP.
- [x] 5 нових unit-тестів на `LoginRateLimiterService` + оновлений `AuthControllerTest` (окремий тест на 429-шлях, підтверджує що `AuthService` взагалі не викликається під час блокування).

### 8.3 Публічний дефолтний JWT secret — ✅ пом'якшено
Значення в `application.yml` — фіксований рядок, видимий кожному, хто клонував репозиторій. Якщо задеплоїти без встановленої env-змінної `JWT_SECRET`, будь-хто може підписати собі власний ADMIN-токен цим відомим ключем. Це системна межа (не код-баг — секрет за визначенням не можна "захистити" в публічному репозиторії), тому повне рішення — обов'язково виставити `JWT_SECRET` при деплої. Код-рівневе пом'якшення:
- [x] `JwtUtil` тепер порівнює активний secret із відомим дефолтом при старті і, якщо збігається, пише голосне `WARN` у логи — більше не можна випадково задеплоїти з дефолтом непомітно.

### 8.4 CORS: зайвий `allowCredentials(true)` — ✅ виправлено
`corsConfigurationSource()` мав `allowedOriginPatterns("*")` (via reflection, не буквальний `*`) **разом з** `allowCredentials(true)` — дозволяє credentialed cross-origin запити з будь-якого сайту. Автентифікація тут — Bearer-токен, що вручну кладеться в заголовок з JS (не cookie), тож credentials браузеру нема чого возити автоматично — прапорець був суто зайвим розширенням поверхні атаки без жодної функціональної користі.
- [x] `allowCredentials` → `false`. Перевірено живим Playwright: реальний логін через `index.html` (крос-origin `localhost:8000` → `localhost:8080`) — токен встановлюється, редірект на `worker.html`, 0 помилок консолі.

### 8.5 SQL/JPQL-ін'єкції — перевірено, чисто
Грep по всьому `src/main/java` на `createNativeQuery`/`@Query(value=`/конкатенацію рядків у запитах — нуль знахідок. Усі `@Query` використовують named-параметри або похідні Spring Data методи.

### 8.6 XSS через `innerHTML` — ✅ виправлено
Пройдено систематично по всіх трьох файлах: `manager.js` (42 місця), `worker.js` (30), `tv.js` (12).
- [x] Додано спільний `escapeHtml()` у `api.js` (завантажується першим на всіх трьох сторінках). Обгорнуто всі інтерполяції вільного тексту (причина браку, ім'я воркера/партнера/матеріалу/вузла/дільниці/поста, номер серії, статуси) — і в текстовому вмісті, і окремо там, де значення потрапляє в **атрибут** (`data-code="${...}"` тощо, де неекранована `"` могла б розірвати атрибут).
- [x] **Найсерйозніша знахідка**: `manager.js` мав `onclick="window.state.activeAssemblyId='${a.id}'; showToast('...${a.name}...', 'info');"` — вільний текст (`a.name`) інтерпольований **прямо в JS-рядковий літерал всередині inline-обробника**. Звичайне HTML-екранування тут **не рятує**: браузер декодує HTML-сутності атрибута (`&#39;` → `'`) ще на етапі парсингу, до того як цей рядок піде на компіляцію як JS — тобто екранована лапка все одно "розкриється" назад у справжню лапку й розірве рядковий літерал. Правильний фінш — прибрати inline JS зовсім: замінено на `data-id` + делегований обробник `.btn-select-assembly` (той самий патерн, що вже використовується для `.btn-load-assemblies`/`.btn-select-task` по всьому коду), ім'я вузла для тосту тепер береться з `state.dataCache.assemblies` за id, а не з розмітки.
- [x] `showToast(message)` (дубльована функція в обох файлах) тепер екранує на самому "стоку" — це автоматично захищає **усі** виклики по всьому застосунку, включно з тими, що показують `err.message` з бекенду, без потреби латати кожен виклик окремо.
- [x] **Перевірено живою атакою, не лише рев'ю коду**: створено серію з номером `XSS-TEST-<img src=x onerror=alert(1)>` і брак з причиною `<img src=x onerror="window.__xss_fired=true">` через реальні API-виклики, відкрито відповідні вкладки в manager.html через Playwright. Результат: `window.__xss_fired` — `false` на кожному кроці, жодного діалогу, в HTML-джерелі значення видно як `&lt;img src=x onerror=...&gt;` (інертний текст), а видимий текст коректно показує оригінальний рядок як звичайні символи.
- [x] Повний регрес: усі 3 режими пройдені Playwright (11 вкладок менеджера, реальний PIN-логін працівника через index.html, ТВ-дашборд) — 0 помилок консолі.

## 10. 🎬 Приймальне тестування — 7 "what if" питань чек-ліста

Раніше значилось як "частково перевірено" (лише через race condition з §7). Пройшовся по кожному явно й перевірив живими даними, а не здогадкою:

1. **Оператор забув натиснути «завершено» — залишиться відкритим на ніч?** Так, і це не проблема: задача просто лишається `IN_PROGRESS` без жодного автотаймауту чи побічної деградації стану. Не потребує фіксу.
2. **Матеріалу не вистачає — чи блокує система старт?** ✅ Так — `createIndividualTask`/`createBatch` резервують матеріали одразу; при нестачі задача йде в `BLOCKED` (§2.4, покрито unit-тестами).
3. **ВК-Метал не повернув за 30 днів — чи бачить керівник тривогу?** ✅ Так — `overdueOutsource` на дашборді й ТВ-слайді "Проблемні зони" з червоним бейджем "Прострочено" (перевірено Playwright під час ТВ-фіксів §7).
4. **Серія на 100 виробів — чи не зависає дашборд?** ✅ Перевірено щойно живим тестом: створення серії на 100 виробів — 0.35с, `GET /api/dashboard` — 20мс, `GET /api/tasks` (303 задачі) — 14мс, повний рендер дашборду в браузері (Playwright) — без зависань, 0 помилок консолі.
5. **Оператор помилково натиснув «завершено» — чи можна скасувати?** ❌ **Ні.** Реальна, підтверджена прогалина — див. §6 вище. Свідомо не фіксив без рішення щодо обсягу.
6. **Стапель заповнений — чи оператор бачить чергу?** ✅ Так — `postLoads[].queue` на дашборді й ТВ-слайді "Завантаження постів", `ResourceConstraintService` блокує старт задачі понад місткість поста.
7. **Два оператори одночасно сканують один піддон — хто виграє?** ✅ Виправлено раніше цієї сесії — `PESSIMISTIC_WRITE`-лок у `TaskRepository.findByIdLocked` (§7, наскрізні знахідки).

**Підсумок: спершу 6 з 7 підтверджено робочими, 1 — реальна прогалина (п.5). Виправлено в §11 нижче — тепер 7 з 7.**

### 11.1 Скасування помилково завершеної задачі

### 11.2 Кнопка "Змінити пароль" — була мертвою через розбіжність CSS-класів

Корінна причина: `#modal-change-password` і `#modal-change-worker-pin` мали зовнішній `<div class="modal-overlay">`, обгортку без жодного CSS-правила, замість `class="modal"` — а видимість у цій кодовій базі керується правилом `.modal.active { opacity:1; pointer-events:auto }`. JS коректно робив `classList.add('active')`, просто на елемент, якого це правило не стосувалось. Working-приклад (`qr-modal`, `detail-modal`) вже існував у тому ж файлі — структуру обох модалок приведено до нього (`class="modal"` на зовнішньому div, `<div class="modal-content glass-card">` всередині).

Заразом виявилась і виправлена суміжна мертва кнопка: `app.closeModal`/`app.openModal` викликались з HTML (`onclick="app.closeModal('qr-modal')"`), але ніде не були визначені в `manager.js` — кнопка закриття QR-модалки нічого не робила. Додано обидва методи в `window.app`.

Функціонально це вже підтримувало зміну пароля **будь-якої ролі**, а не тільки WORKER — `GET /api/workers` (яким наповнюється таблиця "Працівники") повертає всіх, `POST /auth/set-pin` вимагає лише `MANAGER`/`ADMIN` без обмеження на роль цілі. Перевірено Playwright: таблиця "Працівники" показує рядки з ролями WORKER/DISPATCHER/MANAGER/ADMIN, кнопка "Змінити пароль" у кожному рядку відкриває модалку й успішно міняє PIN (перевірено реальним логіном з новим PIN після зміни). Самообслуговування (кнопка в шапці) теж перевірено тим самим способом.

## 14. 📺 ТВ-роль на бекенді — ✅ виправлено

Користувач уточнив: ТВ-дисплей — не моя надбудова понад ТЗ, а його власна вимога, додана ще до початку роботи разом (просто не описана буквально словом "ТВ" в жодному документі). §13 помилково класифікував це як поза межами запиту — виправлено.

**Корінна проблема** (задокументована ще в ІТ-аудиті §12.1 M1, але раніше свідомо не фіксилась): вхід на екран ТВ використовував ТОЙ САМИЙ PIN-логін, що й будь-яка інша роль — хто б не вводив свій PIN на картці "ТВ-Дашборд", у URL (`tv.html?token=...`) опинявся токен саме ЙОГО реальної ролі й прав. Якщо налаштовував менеджер — токен менеджера з повними правами жив у URL і `localStorage` на публічному екрані цеху необмежено довго.

- [x] Новий `SystemRole.TV` — не людина, окремий тип акаунту для дисплея. Навмисно **нуль** явних дозволів у всій системі (жоден `@PreAuthorize` його не згадує) — отже за замовчуванням заблокований на кожній дії, крім трьох ендпоінтів, які й так відкриті для будь-якої автентифікованої ролі й саме їх реально використовує `tv.js` (`/api/dashboard`, `/api/outsource/active`, `/api/events/stream`). Жодних змін у `@PreAuthorize`-анотаціях не знадобилось — модель "явний allow-list" в Spring Security зробила роботу сама.
- [x] `DataSeeder` тепер сіє акаунт "ТВ-Дисплей" (PIN `0000`); менеджер може створити додаткові через звичайну форму реєстрації воркера (додано `TV` в дропдаун — напр. окремий екран для іншого цеху).
- [x] `index.html`: логін на картці "ТВ-Дашборд" тепер перевіряє, що PIN справді належить акаунту з роллю `TV`, і відхиляє з поясненням інакше — той самий патерн, що вже застосований до картки "Менеджер" (перевірка ролі ПЕРЕД видачею токена, а не після).
- [x] **Перевірено живо**: (curl) ТВ-токен → `200` на дашборд/аутсорс, `403` на список працівників/серій-запис/старт задачі; (Playwright) реальний PIN менеджера на ТВ-картці → відхилено з тостом, залишається на index.html; справжній ТВ-PIN → логінить, рендерить дашборд (нулі — свіжий стан після рестарту, не баг), 0 помилок консолі; менеджер створює другий ТВ-акаунт через форму — логіниться коректно.
